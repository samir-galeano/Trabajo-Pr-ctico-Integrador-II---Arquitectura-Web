

\# ADR-009: Base de datos independiente por microservicio



\## Estado

Aceptado.



\## Contexto



La arquitectura propuesta contempla la extracción progresiva de cuatro microservicios: Search, Audit, Export y Media.



Actualmente, BookStack utiliza MariaDB como base de datos principal y concentra información de diferentes funcionalidades dentro de un mismo esquema.



Si los nuevos microservicios acceden directamente a las tablas de BookStack, se generará acoplamiento entre los servicios y se dificultará su evolución independiente.



Se necesita establecer una estrategia de persistencia que respete los límites de cada contexto delimitado.



\## Decisión



Se adopta el patrón Database per Service (base de datos por microservicio).



Cada microservicio será responsable de administrar sus propios datos y tendrá su propio esquema o instancia de base de datos, según las necesidades de implementación.



Se establecen las siguientes responsabilidades:



\- Search: almacenamiento de índices y datos relacionados con las búsquedas.

\- Audit: almacenamiento de registros de actividad y auditoría.

\- Export: almacenamiento de solicitudes, estados y resultados de exportación.

\- Media: almacenamiento de metadatos y referencias de imágenes y archivos adjuntos.



BookStack conservará su base de datos MariaDB independiente.



Los microservicios no podrán consultar ni modificar directamente las tablas de MariaDB de BookStack.



La comunicación e intercambio de información se realizarán mediante API REST y eventos publicados a través del broker NATS JetStream.



\## Alternativas consideradas y rechazadas



\### Base de datos compartida entre todos los microservicios



Se rechaza porque genera dependencias entre servicios, dificulta la independencia de los modelos de datos y aumenta el acoplamiento.



\### Acceso directo de los microservicios a MariaDB de BookStack



Se rechaza porque permitiría que los servicios dependieran de la estructura interna del monolito, dificultando la extracción progresiva y la evolución independiente.



\### Una única base de datos con esquemas separados sin aislamiento de acceso



Se rechaza porque separar esquemas no garantiza por sí solo la independencia. Cada servicio debe controlar sus propios datos y limitar el acceso de los demás.



\## Consecuencias



\### Positivas



\- Reduce el acoplamiento entre microservicios.

\- Permite evolucionar los modelos de datos de forma independiente.

\- Mejora el aislamiento de responsabilidades.

\- Facilita el mantenimiento de cada servicio.

\- Evita que los microservicios dependan directamente del esquema interno de BookStack.



\### Negativas



\- Aumenta la complejidad de administración y respaldo.

\- Puede producir duplicación controlada de información.

\- Requiere mecanismos de sincronización entre servicios.

\- La consistencia entre diferentes bases de datos debe gestionarse mediante eventos y procesos distribuidos.



\## Consideraciones operativas



\- Cada servicio deberá utilizar sus propias credenciales.

\- No se compartirán credenciales de acceso entre microservicios.

\- Los datos se intercambiarán mediante contratos definidos.

\- Se deberán implementar mecanismos de respaldo y recuperación.

\- Los eventos deberán incluir identificadores que permitan correlacionar las operaciones.

\- Se deberá contemplar consistencia eventual.
